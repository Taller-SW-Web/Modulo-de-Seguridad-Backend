## DTO definitivos

Todos pertenecen a `credencial.application.dto`; nunca transportan hash o entidad:

```java
record SecretoEfimero(String valor) {} // toString sobrescrito: REDACTADO
record RevisionCredencial(UUID usuarioId, UUID credencialId, long version) {}
record PreverificacionCredencial(boolean coincide, Optional<RevisionCredencial> revision) {}
record InfraccionPassword(ReglaPassword regla, Integer esperado) {}
record ValidacionPassword(List<InfraccionPassword> errores) {
    boolean valida() { return errores.isEmpty(); } // lista copiada/inmutable
}
enum ReglaPassword {
    LONGITUD_MINIMA, MAYUSCULA, MINUSCULA, DIGITO, CARACTER_ESPECIAL,
    CONTRASENA_COMUN, DATOS_PERSONALES, YA_UTILIZADA
}
```

SecretoEfimero conserva el valor exacto y no debe serializarse, persistirse ni
registrarse. Es de vida de petición; no introducirlo en contexto/auditoría.
Las firmas anteriores muestran los componentes públicos; el código añade
validaciones no-null, versión no negativa y representación redactada.

La revisión utiliza `credencial.usuario_id` y `credencial.version` reales.
En esta persistencia `credencialId == usuarioId`: no existe otra columna id.
Una revisión con otro credencialId no confirma. No usar fecha como revisión.

Una credencial existente devuelve su revisión incluso con coincide=false,
para revalidar antes de registrar un fallo. Usuario/credencial inexistentes
realizan una comparación con hash sintético Argon2id del arranque y devuelven
false sin revisión. Ese material no se persiste ni representa una cuenta.
BCrypt legacy se verifica con las condiciones de T001; no se rehashea al leer.

## Frontera transaccional y ejemplo para MFA

Preverificar realiza el hashing antes de la transacción del coordinador y de
adquirir sus locks.
Confirmar exige transacción ya abierta (MANDATORY) y la cuenta bloqueada por el
coordinador. La confirmación es una consulta escalar de versión actual:
no toma un lock de credencial antes del desafío ni confía en una entidad L1.
Se conserva el orden cuenta → desafío, sin volver a un nivel anterior.

Ejemplo interno de coordinación; no es código añadido a #16:

```java
// Antes de abrir la transacción; UUID resuelto por CuentasPort.
var previa = credenciales.preverificar(Optional.of(usuarioId), secreto);
if (!previa.coincide()) {
    // Recorrido negativo genérico del coordinador; no crear desafío.
    return resultadoNegativoGenerico;
}
var revision = previa.revision().orElseThrow();

// En un bean coordinador distinto, REQUIRED + READ_COMMITTED.
return transaccion.execute(status -> {
    var cuenta = cuentas.bloquear(usuarioId);
    if (!credenciales.confirmarRevision(revision)) {
        // Salir sin efectos. El coordinador puede repetir la preverificación
        // fuera del lock como máximo una vez, según ACUERDOS-INTERNOS.
        return resultadoRevisionCambiada;
    }
    // Revalidar disponibilidad y MFA efectivo con sus dueños antes de crear.
    // Adaptación al DTO exportado HOY por #16; copia exacta, ningún UUID nuevo:
    var revisionMfa = new RevisionCredencialMfa(
        revision.usuarioId(), revision.credencialId(), revision.version());
    return mfa.crearDesafio(cuenta.id(), revisionMfa);
});
```

El ejemplo usa el DTO actual de #16 para mostrar la frontera real. Si la otra
sesión adapta ese contrato para consumir RevisionCredencial directamente, elimina
solo esa conversión. Ambos llevan el mismo usuario_id y versión; no crear un
identificador alternativo ni sustituirlo por timestamp. El ejemplo deja los
resultados negativos al coordinador y no añade códigos HTTP ni nuevas políticas.
Caducidad se evalúa al completar autenticación, no se revela al crear el desafío.
La prueba de MFA correcta vuelve a confirmar la revisión antes de emitir sesión.
