## Diseño

- `sesion.application.service.LoginService` (coordinador) implementa `LoginPort`.
- Consume las capacidades ajenas solo por `sesion.adapter.out.capacidad.PuenteLogin`
  (regla de arquitectura): `CuentasPort` (Eva), `CredencialesPort` (Juan José),
  `ProteccionPort` y `MfaPort` (Luis), `AutorizacionPort` (Sergio); abre la familia con
  `SesionesPort.abrir` en el mismo commit.
- Fuera de locks: cuenta orientativa por correo normalizado (`strip` + minúsculas) y
  preverificación de la contraseña (comparación equivalente si no existe).
- Transacción READ_COMMITTED (`TransaccionLoginSpring`), orden de locks común:
  guard ADMIN (solo si hay que registrar un fallo) → cuenta → protección → credencial
  → MFA/sesión. Los rechazos **confirman** su transacción: el fallo contado persiste
  antes del 401.
- Revisión de credencial o correo cambiados entre la preverificación y el lock: se
  repite una sola vez sin efectos; a la segunda, 401.
- MFA efectivo (voluntario o rol de gestión): solo `DesafioMfa`, sin familia ni reinicio
  de la racha. Sin MFA: caducidad → 403 `PASSWORD_CADUCADA`, `completarLogin` y familia.
- HTTP (`LoginController`): ruta pública; todo rechazo de identidad, cuerpo vacío
  incluido, es el mismo `401 CREDENCIALES_INVALIDAS`; JSON roto 400; fallo de datos
  503 `NO_DISPONIBLE` sin SQL ni secretos.

## Evidencia (15-oct-2026)

- `LoginServiceTest` 9/9 (todas las ramas, orden de locks, repetición única, MFA sin
  familia, caducidad, cuerpo vacío). `LoginHttpTest` 4/4 sobre servidor real.
  Arquitectura y contratos exportados en verde.
- Recorrido real contra PostgreSQL 16 local (base de ensayo de la ventana T002:
  esquema observado + V101–V106 + catálogo + grants del #35), backend como
  **`g7_runtime`**, cuentas de prueba del #33:

| Caso | Resultado |
|---|---|
| A con correo en mayúsculas y espacios | 200, JWT RS256 con `sub=…f00a`, `tipo=acceso`, `roles=[CLIENTE]`, 900 s; `kid` presente en el JWKS |
| A con contraseña errónea / correo inexistente | el mismo 401 `CREDENCIALES_INVALIDAS` |
| Refresh / reúso del refresco viejo / el nuevo tras el reúso | 200 rotado / 401 / 401 (familia revocada) |
| B logout y luego refresh | 204 / 401 |
| ADMIN_SISTEMA | 200 solo `DesafioMfa` (sin tokens) |
| V (VENDEDOR sin CLIENTE) | 200 con `roles=[VENDEDOR]` |
| L tras 5 fallos distintos | **pendiente**: el quinto fallo necesita los efectos del bloqueo (ver abajo) |

El recorrido encontró dos fallos de permisos en los grants del #35, ya corregidos allí:
lectura de `usuario_estado_efectivo` y el lock del guard ADMIN sobre `rol`.
